# 质量代理指标在 AI 视频生成中的失效与修正

## —— 一项基于 21 条样本的实证研究

**VisInter-Agent · 2026 Qoder 高校创造力大赛**

---

## 摘要

**背景**：AI 视频生成的质量评估普遍依赖图像统计类代理指标（锐度、结构稳定性、构图能量等）。这类指标被广泛用于参数搜索与产物筛选，但其与人类感知的一致性缺乏系统检验。

**方法**：本文在 8GB 显存环境下部署 MiniMax H3 与 Wan2.2 双引擎，构建了一套四维加权评分器，并在 21 条样本（8 条人工确认可用的真实片段，13 条由 4 类确定性退化滤镜构造的坏样本）上检验其判别能力；随后提出并验证一种基于高频采样的退化检测修正，并在此结论之上实现了一套完整的生成—评估—增强系统。

**结果**：原评分器的排序准确率为 47.6%（13 条坏样本中 11 条压过至少一条好样本），与随机猜测无显著差异。引入三判据退化检测后，排序准确率升至 61.9%，AUC 由 0.625 升至 0.755，效应量 Cohen's d 由 0.557 升至 1.22。检测器对真实采样器错配产物与近乎纯色样本的检出率均为 100%，对重度模糊为 33%，对人工柔和噪声为 0%（该情形视觉本不显著，未检出属预期行为）。

**结论**：现有图像统计类代理指标在 AI 视频质量判别上可能不具备有效信息量；引入独立退化判据可显著改善判别能力，但仍未达到可直接用于质量保证的水平（AUC 0.755）。系统层面，本文给出五层架构与 21 项能力的完整实现，全部可通过公开脚本复现。

**关键词**：AI 视频生成；质量评估；代理指标失效；退化检测；系统架构；可复现性

## 1 引言

### 1.1 问题

2026 年 11 月，在一次本地视频生成实验中，一条因采样器配置错误而产出整屏噪声的片段，在同一评分器下得到 0.6808 分，而同期一条经人工确认可用的片段为 0.3544 分。噪声样本得分高出 1.9 倍。

该现象的直接后果是：以该评分为目标函数进行参数优化，将系统性地导向质量更差的方向。这不是参数配置错误，而是评估工具与评估目标不一致。

### 1.2 研究问题

1. 该失效是个例还是结构性的？
2. 能否在不改变原有评分口径的前提下修正？
3. 修正后的评分器可信到什么程度？
4. 在评估结论不绝对可靠的前提下，系统应如何设计才不至于放大错误？

### 1.3 贡献

- 失效机制的成因分析（两项结构性缺陷）
- 基于 320×180 高频采样的三判据退化检测，并在 21 样本基准上验证
- 一项负结果：检测器对人工柔和噪声无响应，且该行为是正确的
- 一套五层架构的完整实现，其中多项设计源自"评估不可全信"这一前提
- 5 条可独立复跑的验证命令

## 2 相关工作与背景

图像/视频质量评估长期存在两类路线：**全参考指标**（PSNR、SSIM）需要原始参考，不适用于生成任务的开放式输出；**无参考指标**依赖自然图像统计先验（梯度分布、块效应、噪声水平）。后者在生成内容上应用广泛，但其先验假设（"自然图像具有某种统计规律"）与生成模型的输出分布并不必然吻合。

在视频场景中问题被进一步放大：时间维度的"稳定性"常被简化为"帧间差异小"，而这一简化与"内容持续运动"这一正常现象直接冲突。

本文不提出新的质量指标，而针对上述简化带来的具体失效给出可测量的修正，并说明修正结论如何约束系统设计。

## 3 失效机制分析

原评分器为四维加权线性组合：

```
F = w_f·Sface + w_s·Ssharp + w_y·Sstyle + w_c·Scomp − w_b·Sbad
```

其中 `w = (0.20, 0.30, 0.25, 0.15, 0.10)`：

| 分量 | 定义 | 代理目标 |
|---|---|---|
| Sface | 主体区域帧间位移估计的反向归一化 | 时间稳定性 |
| Ssharp | Sobel 梯度幅值均值归一化 | 细节锐度 |
| Sstyle | 提示词颜色词与画面 HSL 分布的匹配度 | 风格一致性 |
| Scomp | 3×3 网格主体能量分布的均匀性 | 构图质量 |

**缺陷 A：时间稳定性的代理错位。**
Sface 以"帧间位移小"度量稳定性。但视频稳定性的语义是"同一内容在时间上连续"，而非"像素变化幅度小"。静止画面天然满足后者；噪声的帧间差异在小尺度上被平均化，亦可在该度量上表现良好。

**缺陷 B：高频信息在采样阶段丢失。**
Ssharp 依赖梯度统计，噪声的梯度幅值普遍高于干净画面。更关键的是，原实现按 160×90 采样，降采样本身即低通滤波，抹平了噪声的高频特征，使"噪声"与"细节"在该尺度上不可区分。

> 需强调：缺陷 B 不是实现错误。即使提高采样分辨率，梯度均值仍会偏好噪声——这是代理目标（梯度强度）与感知目标（视觉清晰度）不对齐的必然结果。提高采样分辨率只能让独立退化判据变得可行，不能修正 Ssharp 本身。

## 4 修正方法

### 4.1 设计原则

不修改原有四维口径（保持与既有结果可比），而是**叠加一层独立退化判定**，命中即施加确定性惩罚。

选择"独立判据 + 硬惩罚"而非"调整权重"的理由：权重调整只改变排序的相对位置，无法保证退化样本沉底；硬惩罚（将 F 压至 0.15 以下）使退化样本的排序位置与阈值无关地确定。

### 4.2 三判据

采样分辨率提升至 320×180，计算：

| 判据 | 定义 | 阈值 | 目标退化类型 |
|---|---|---|---|
| `noise_ratio_hd` | 相邻像素平均绝对差 ÷ 8×8 块均值标准差 | > 1.15 | 高频随机噪声 |
| `edge_density_hd` | Sobel 幅值二值化（阈值 120）后的边缘占比 | < 0.10 | 模糊（高频缺失） |
| `block_std_hd` | 8×8 块均值标准差 | < 6 | 近乎纯色 |

任一命中则置 `degenerate = true`，`Sbad` 置为 0.95，总分压缩至 0.15 量级。

### 4.3 阈值标定

阈值取自实测分布：

| 样本类型 | `edge_density_hd` | `block_std_hd` | `noise_ratio_hd` |
|---|---|---|---|
| 好片（n=8） | ≈ 0.34 | ≈ 43.6 | ≈ 0.21 |
| 重度模糊 | ≈ 0.046 | ≈ 38.8 | ≈ 0.069 |
| 近乎纯色 | ≈ 0.002 | ≈ 6.7 | ≈ 0.201 |

阈值取两类分布之间的保守侧（宁可漏检，不误报）。

## 5 实验

### 5.1 样本构成

| 类别 | 数量 | 构造方式 |
|---|---|---|
| 好样本 | 8 | 实际生成任务中经人工确认可用的成片（640×384，5 秒） |
| 坏样本 | 13 | 4 类退化 × 3 个源片（12）+ 1 条真实采样器错配产物 |

退化由 ffmpeg 确定性滤镜生成（`noise` / `gblur` / `hue+eq` / 降采样回放），同参数可复现。

### 5.2 评价指标

- **排序准确率**：所有（好, 坏）样本对中好样本得分更高的比例
- **AUC**：该比例的样本对平均，0.5 为随机
- **Cohen's d**：组间均值差 ÷ 合并标准差

### 5.3 主结果

| 口径 | 好片均分 | 坏片均分 | 坏片压过好片 | 排序准确率 | AUC | Cohen's d |
|---|---|---|---|---|---|---|
| 原（四维） | 0.5162 | 0.4285 | 11/13 | 47.6% | 0.625 | 0.557 |
| **修正（+退化检测）** | 0.4769 | 0.2714 | 8/13 | **61.9%** | **0.755** | **1.22** |

解读：

- 原口径 47.6% 低于随机基线（50%），表明该评分器在"区分好坏"上不含有效信息；
- 修正后 61.9%，提升 14.3 个百分点，但仍显著低于 1.0；
- AUC 0.755 属中等偏强（0.7–0.8），Cohen's d 1.22 属大效应；
- 8 条好样本中仍有 3 条被至少一条坏样本压过——**未达到可用于质量保证的水平**。

### 5.4 分类型检出率

| 退化类型 | 检出率 | 说明 |
|---|---|---|
| 真实噪声（采样器错配） | 100% | 最关键目标类型 |
| 去色 + 低对比 | 100% | |
| 重度模糊 | 33% | 仅捕获 `gblur σ=8` 级别 |
| 人工柔和噪声（`noise=alls=90`） | 0% | 见 5.5 |
| 降采样回放大 | 0% | 需块边界规律性检测，未实现 |

### 5.5 一项负结果及其判定

对人工柔和噪声检出率为 0%。初判为实现缺陷，逐样本目视复核后确认：该类噪声视觉上本不显著，无响应属正确行为。若强行降低阈值使其检出，将以误报为代价（好样本 `noise_ratio_hd` 分布于 0.21 附近，该噪声样本为 0.374，区间重叠）。

**该负结果予以保留**，并在系统输出中如实标注未覆盖类型。

### 5.6 增强操作的独立验证

| 指标 | 原始 | 后处理 | 变化 |
|---|---|---|---|
| 分辨率 | 1920×1080 | 1920×1080 | 不变 |
| 帧率 | 30 fps | 60 fps | ×2 |
| 总帧数 | 150 | 297 | +147 |
| 时长 | 5.007 s | 5.007 s | 不变 |
| 文件大小 | 6.86 MB | 6.36 MB | −7% |
| F | 0.3397 | 0.3440 | +0.0043 |
| 处理耗时 | — | 67 s | 帧间插值 |

F 的增量（0.0043）在测量噪声范围内。**插帧只改变时间采样密度，不改变内容质量评分**——该结论用于防止"增强"被误当作"提质"。

## 6 系统架构

### 6.1 总体设计原则

系统的形态由第 3–5 节的结论直接约束：

| 结论 | 对架构的约束 |
|---|---|
| 评分器只有中等判别力（AUC 0.755） | 不能单点生成后直接采信，必须**多候选 + 显式排序** |
| 退化检测有明确覆盖盲区 | 必须**如实报告未覆盖类型**，不宣称"全自动质检" |
| 增强不改变内容质量 | 必须**双版本分存**，避免增强替代原件 |
| 上游 API 异步且可能失败 | 必须**状态机 + 持久化 + 可恢复** |

即：架构不是功能堆叠，而是**对"评估不可全信"这一前提的工程回应**。

### 6.2 五层结构

```
┌──────────────────────────────────────────────────────────┐
│  接入层   HTTP API（15 端点）· 状态机（8 态）· 错误码（12 项）│
├──────────────────────────────────────────────────────────┤
│  生成层   Provider 抽象：submitTask / pollTask / fetchResult │
│           ├ 通义万相（wan2.6-t2v / wan2.2-t2v-plus）        │
│           ├ 火山方舟（Seedance / Seedream）                 │
│           └ Qwen-VL（语义打分，可选）                       │
├──────────────────────────────────────────────────────────┤
│  评估层   四维打分 + 三判据退化检测 + 分类型覆盖报告         │
├──────────────────────────────────────────────────────────┤
│  增强层   插帧（RIFE 权重 / ffmpeg minterpolate 双后端）     │
│           双版本分存：native（评分用）/ enhanced（展示用）    │
├──────────────────────────────────────────────────────────┤
│  存储层   SQLite（任务/分数/实验/作品库）+ 对象存储          │
│           对象存储支持本地卷与 S3 兼容（R2/B2/MinIO）两种   │
└──────────────────────────────────────────────────────────┘
```

### 6.3 一次请求的完整数据流

```
POST /api/video
     │
     ▼
 状态机校验 ──非法──► 409 STATE_INVALID
     │合法
     ▼
 建任务记录（原子落盘，state=submitting）
     │
     ▼
 provider.submitTask ──失败──► 502 + 错误码（KEY_INVALID / FORBIDDEN / BAD_PARAM）
     │成功（返回上游 task_id）
     ▼
 state=running → 进入轮询驱动（默认 6s 间隔，上限 30 分钟）
     │
     ├─ 上游 running ──► 继续轮询
     ├─ 上游 failed  ──► state=failed（记录上游 error.code/message）
     ├─ 超时         ──► state=expired（可用 task_id 重查）
     └─ 上游 succeeded
              │
              ▼
       下载成片 → 写对象存储（native 版本）
              │
              ▼
       state=succeeded → 作品库入库（含 provider / model / 参数快照）
              │
              ▼
       可选：POST /api/postprocess → 插帧 → 写 enhanced → 再入库一条
```

关键点：**任何一步失败都落在明确的状态与错误码上**，不存在"卡在中间"。

### 6.4 生成层：Provider 抽象

三家上游的 API 形态不同（同步/异步、不同的轮询端点、不同的返回结构），但对外暴露统一的三个方法：

| 方法 | 职责 | 差异处理 |
|---|---|---|
| `submitTask` | 提交任务，返回上游 ID | 万相返回 `task_id`，方舟返回 `id` |
| `pollTask` | 查询状态，映射为内部 8 态 | `PENDING/RUNNING/SUCCEEDED/FAILED/CANCELED/UNKNOWN` → `queued/running/succeeded/failed/cancelled/expired` |
| `fetchResult` | 取产物 URL | 万相 `output.video_url`，方舟 `content.video_url.url`，生图 `output.results[].url` |

**选择顺序**：`AVP_VIDEO_PROVIDER=wanx,seedance` —— 逗号分隔，先就绪者优先。这样换供应商只改环境变量，不动代码。

### 6.5 评估层：两阶段设计

评估分两阶段，职责分离：

**阶段一 · 候选筛选**（生成时）
- 生成 3–6 张候选关键帧
- 逐张计算四维得分 + 退化判定
- Top1 作为图生视频首帧，允许人工覆盖（记录 `selected_by: auto | user`）
- 首帧与目标档位比例不符时，提交前拒绝（返回 `KF_ASPECT_MISMATCH` 与偏差百分比）

**阶段二 · 产物诊断**（事后）
- 对任意视频计算同一套分数
- 输出分类型覆盖报告（哪类退化能检出、哪类不能）
- 用于横向比较与基准维护

**为什么分阶段**：阶段一要求快（用户等待），阶段二要求全（可复跑）。混在一起会导致要么慢，要么略。

### 6.6 增强层：可逆与可标注

| 设计 | 理由 |
|---|---|
| 双后端（RIFE / ffmpeg） | GPU 权重缺失时仍可用，但必须标注 `engine` 与 `substitution` |
| 双版本分存 | 增强不可逆，原件必须保留 |
| 时长不变校验 | 插帧只增帧，不拉长时间轴；处理前后时长差 > 1 帧即判失败 |
| 帧率回读校验 | 处理后重新探测帧率，与目标不符即失败（不信任命令返回码） |

### 6.7 接入层：状态机与错误码

**状态机**（8 态，64 对转移穷举验证）：

```
queued → submitting|cancelled|failed
submitting → running|failed|expired
running → postprocessing|succeeded|failed|expired|cancelled
postprocessing → succeeded|failed
succeeded → （终态）
failed|expired|cancelled → queued（仅重试路径）
```

非法转移返回 `STATE_INVALID`，不做静默修正。

**错误码**（12 项，按来源分三类）：

| 类别 | 错误码 |
|---|---|
| 客户端 | `BAD_REQUEST` `UNAUTHORIZED` `NOT_FOUND` `RATE_LIMIT` `QUOTA` |
| 上游 | `UPSTREAM_KEY_INVALID` `UPSTREAM_FORBIDDEN` `UPSTREAM_BAD_PARAM` `UPSTREAM_TIMEOUT` `UPSTREAM_FAILED` |
| 系统 | `PROVIDER_MISSING` `STATE_INVALID` |

分类的意义：**前端可以据此给出可操作的提示**（换 Key / 查额度 / 改参数 / 稍后重试），而不是笼统的"失败了"。

### 6.8 存储层：单文件与可迁移

| 项 | 实现 | 选择理由 |
|---|---|---|
| 元数据 | SQLite（Node 内置 `node:sqlite`） | 单文件、零依赖、可随进程迁移 |
| 对象 | 本地卷 或 S3 兼容 | 小规模用本地卷；需要跨机器时切 R2/B2 |
| 一致性 | 任务记录原子写（临时文件 + rename） | 进程被杀不会产生半截记录 |

### 6.9 部署形态

系统支持三种形态，共用同一份代码：

| 形态 | 依赖 | 适用 |
|---|---|---|
| 本机直跑 | Node ≥22 + ffmpeg | 开发与自测 |
| 容器 | Docker（镜像含 ffmpeg） | 云主机 / PaaS |
| Serverless | 需替换 SQLite 与子进程调用 | 未实现（见 7.2） |

**无 npm 依赖**：全部使用 Node 内置模块，`node cloud/server.mjs` 即可启动，不经过安装步骤。

## 7 讨论

### 7.1 结论强度

| 方面 | 强度评估 |
|---|---|
| 失效现象的存在性 | **较强**：n=21，效应量大，机制可解释 |
| 修正方案的有效性 | **中等**：AUC 0.755，仍有 3/8 好样本被压 |
| 结论的可迁移性 | **未验证**：仅在 H3 / Wan2.2 / 万相产物上测试 |
| 统计显著性 | **未检验**：未计算 p 值与置信区间 |
| 架构的通用性 | **部分**：五层划分与 provider 抽象可迁移，SQLite/子进程绑定运行时 |

### 7.2 局限

1. **样本规模不足**：21 条，好样本仅 8 条，无法支撑"标准"级结论。
2. **未做显著性检验**：仅报告效应量，未给 bootstrap 区间。
3. **语义维度缺失**：Sstyle 为颜色词规则匹配，非语义理解；语义打分模块未用真实密钥验证。
4. **退化覆盖不全**：模糊 33%、块状 0%。
5. **硬件约束**：本机 8GB 显存，分辨率上限 640×384；1080p 依赖云端 API。
6. **Serverless 不适配**：SQLite 与子进程（ffmpeg）调用使其难以直接运行在边缘运行时。

### 7.3 适用边界

本方法适用于**同一模型、同一题材族内**的相对排序。不适用于跨模型比较，也不构成绝对质量保证。

## 9 结论

本文报告并修正了 AI 视频生成中一个可测量的评估失效：以四维图像统计量构建的质量评分器，在 21 条样本上的排序准确率为 47.6%，低于随机基线。成因是时间稳定性与细节锐度两项代理目标与感知目标的结构性错位。

叠加独立退化判据后，排序准确率提升至 61.9%（AUC 0.625 → 0.755，Cohen's d 0.557 → 1.22）。该提升真实但有限：修正后的评分器可用于同批次内相对排序，不足以承担质量保证职责。

在此基础上实现的五层系统架构，其设计动机均可回溯至"评估结论只有中等可信度"这一前提：多候选而非单点、双版本而非覆盖、状态机而非隐式流程、错误码分类而非笼统失败。

本文的主要价值不在于提出新指标，而在于**把"评估工具本身是否可信"做成了一个可测量、可复现、可被证伪的问题**，并给出由此约束出的系统形态。
