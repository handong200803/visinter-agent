# 本地一体化 AI 视频生成平台 · 最优设计方案 v1.0

> 定位：装在自己电脑上的「商用级短视频产线」。自识别硬件 → 自动配置 → 一键出 1080p 成片。
> 参考机型 T0：RTX 5060 Laptop / 8GB / sm_120 / 驱动 576.80 / D 盘 419G

---

## 0. 五条不可妥协的设计原则

1. **不造引擎**：ComfyUI 作为进程级推理内核（HTTP/WS 调用，零 fork），前端与模板层全部自研 → 可闭源商用，且永久跟随上游模型生态。
2. **中文是母语**：中文进、中文出，中文提示词引擎是产品核心而非附属功能。
3. **画质靠管线不靠单模型**：关键帧 → i2v → 补帧 → 超分 → 质检 → best-of-N，单点模型再好也到不了商用。
4. **显存是硬约束，不是提示**：所有参数由求解器算出，用户永远不会看到 OOM。
5. **每一帧可复现**：seed + 完整参数快照 + 模型 sha256 入库，客户半年后要求重出必须一模一样。

## 2. 显存自识别 → 自动配置（核心差异化）

### 2.1 三段式：探测 → 求解 → 自学习

**A. 探测（首启 + 每次启动校验，<1.5s）**

```python
# scripts/probe_gpu.py  ← 落地文件
import json, subprocess, torch
def probe():
    name, total, cc, drv = subprocess.check_output([
      "nvidia-smi","--query-gpu=name,memory.total,compute_cap,driver_version",
      "--format=csv,noheader,nounits"], text=True).strip().split(",")
    torch.cuda.init()
    free, t = torch.cuda.mem_get_info(0)       # 真实可用，不是 total
    return {
      "gpu": name.strip(), "vram_total_mib": int(total),
      "vram_usable_mib": free // 2**20,        # WDDM 已扣桌面占用
      "compute_cap": float(cc), "driver": drv.strip(),
      "torch": torch.__version__, "cuda": torch.version.cuda,
      "fp8": float(cc) >= 8.9, "fp4": float(cc) >= 12.0,
      "ram_gib": round(psutil.virtual_memory().total/2**30),
      "disk_free_gib": shutil.disk_usage(MODEL_ROOT).free//2**30,
      "pcie_gen": "gen4",  # nvidia-smi --query-gpu=pcie.link.gen.max
    }
```

三条硬规则：
- **只看 `mem_get_info`**：Windows WDDM 下 8151MiB 实际可用约 6.6–7.2G。
- **sm_120 → 强制 cu128 轮子**：Blackwell 50 系，安装器断言 `torch.version.cuda >= 12.8`，否则自动换轮子（当前本机是 `2.15.0+cpu`，属未就绪状态）。
- **禁止 sysmem fallback**：溢出到内存会慢 10 倍，宁报错降档。

**B. 求解（显存预算方程反解最大可行组合）**

```
peak(res, frames) ≈ W_model(model, quant)
                  + A_act(res, frames) * k_attn(backend)
                  + V_dec(res, frames, tile)
                  + F_ctx(overhead)
```
- `W_model` 查表（每模型每量化实测值，见 §3）
- `A_act ≈ c1·res_pixels·frames/1e6`（c1 按架构标定，Wan≈、Hunyuan≈ 分开存）
- `V_dec`：分块解码时 ≈ `c2·tile_pixels`，不分块时 `c2·res_pixels·frames`
- 目标是 `peak ≤ vram_usable × 0.92`（留 8% 安全垫）

求解顺序：**先保画质（分辨率），再保时长（帧数），最后保步数**；每档给三套预设 `draft / standard / cinematic`。

**C. 自学习（跑完 3 条就修正）**

每完成一个任务，采集 `torch.cuda.max_memory_allocated`（Worker 侧上报）、实际耗时、是否 OOM，写入
`device_profile.json`（按 `sha1(gpu_name+driver+torch+模型清单)` 指纹缓存）：

```json
{
  "fingerprint": "sha1:...", "tier": "T0",
  "calibrated": {"2026-11-16": {"wan2.1-1.3b/fp16/480p/49f":
     {"peak_mib": 6980, "sec": 168, "ok": 5, "oom": 0}}},
  "user_pref": {"quality_bias": "cinematic"}
}
```
首次装机跑 3 条极短标定片（64 帧 256p，累计 <40s），把系数从默认值校正到本机真值。
**这份 profile 可导出/导入 → 用户社区互换"同机型最佳配置"**，是低成本的增长点。

### 2.2 自动降级决策树（用户不可见）

```
OOM/超时 → ① 帧数 −25% → ② 分辨率降一档 → ③ 同族换小模型
        → ④ 量化升一档(Q4→Q3) → ⑤ 开 block-swap → ⑥ 分块生成+拼接
        → ⑦ 挂起 + 一行中文解释 + 三选一建议(降画质/加时间/换模型)
```
每次降级前端只显示一句人话：「8G 显存下 720p/5s 会超出，已自动改为 576p/4s + 2× 超分，成片仍为 1080p」。

## 4. 商用画质管线（回答"质量非常高"）

单模型永远到不了商用。真正的画质来自 **七道工序**：

```
① 中文提示词 → 结构化分镜脚本（LLM）
② 关键帧 T2I（东方审美 LoRA + 角色锚点）
③ 一致性锁定（角色参考图 + IPAdapter/首帧锁定）
④ i2v 生成（运动幅度/运镜受控）
⑤ best-of-N（N=3）→ VLM 审美评分选最优
⑥ 后处理链：deflicker → 光流稳定 → RIFE 补帧 → 2× 超分 → 调色 LUT/颗粒
⑦ QC 质检门 → 不合格自动重跑（换 seed / 调强度）
```

**best-of-N + VLM 评分**（商用级的关键工程手段）
- 同 prompt 跑 3 条，用 Qwen3-VL 按 5 维打分：构图 25 / 主体保真 25 / 运动自然 20 / 画质锐度 15 / 一致性 15
- 取 top-1，原始评分入库（用于后续 LoRA 微调与模板权重优化）
- 代价：时间 ×3；对策：草稿档 N=1，商用档 N=3，影视档 N=5

**QC 质检指标（自动化，全部可脚本化）**

| 项 | 判据 | 处置 |
|---|---|---|
| 黑屏/白屏 | 平均亮度 <12 或 >243，或单帧骤变 >60% | 重跑 |
| 闪烁 | 帧间亮度时序 std 超阈值 | deflicker + 重跑 |
| 糊/运动模糊 | 拉普拉斯方差 < 阈值（逐帧中位数） | 提高步数/降运动幅度 |
| 人脸崩坏 | 检测失败或关键点抖动 > 阈值 | 换 seed / 降幅度 |
| 文字乱码 | OCR 置信度低 | 改由后期字幕烧录 |
| 音画对位 | 分窗 RMS 静默窗偏移 | 重排时间轴 |
| 角色一致性 | 首末帧 DINO 相似度 < 0.72 | 加 IPAdapter 权重 |

装配复用本机已有原子件：`media-verify`（亮度/astats 核验）、`video-compose`（manifest 合成）、`video-cover`（双平台封面）、`image-to-video`（低配兜底运镜）。

**交付规范**：H.264 High / H.265 可选 · 24/30/60fps · Rec.709 · 响度 −14 LUFS（平台）/−23 LUFS（广电）· `+faststart` · SRT · 封面 · manifest.json。

## 5. 中文提示词引擎（"贴切"的工程实现）

### 5.1 LLM 选型（本地优先，云端可插拔）

| 档 | 模型 | 部署 | 说明 |
|---|---|---|---|
| 轻 | Qwen3-4B-GGUF Q4 | llama.cpp | 8G 卡 CPU/GPU 混合，<2s |
| 标 | **Qwen3-14B** 或 Qwen3-30B-A3B | Ollama/llama.cpp | 中文语义最强档，MoE 激活 3B 速度快 |
| 高 | 云端 DeepSeek / GLM / 豆包 | API | 一键切换，隐私敏感时禁用 |
| 评分 | Qwen3-VL-8B | 同机 | best-of-N 审美打分 |

选型理由：中文影视术语、成语/意象理解、JSON 结构化输出，Qwen3 系列目前开源第一梯队。

### 5.2 提示词引擎的四件事

1. **意图解析** → JSON：`{主体, 动作, 场景, 时代, 风格, 景别, 运镜, 光线, 情绪, 时长}`
2. **影视语言补全**：景别（特写/中景/远景）、运镜（推/拉/摇/移/环绕）、光比、色温、焦段、镜头质感
3. **双轨输出**（关键）：`zh_direct`（Wan/Hunyuan 可直接吃中文）+ `en_encoded`（LTX/CogVideoX/Flux 用英文）+ `neg`（负向词库）
4. **跨镜头锚点**：同一角色的 `{外貌锚点, 服装锚点, 光调锚点}` 写入项目级记忆，保证 10 个镜头是同一部片

### 5.3 系统提示词骨架（直接可用）

```
你是资深中文影视分镜师与 AI 视频提示词工程师。把用户口语句子改写成可执行的镜头提示词。
硬性规则：
1) 只输出 JSON，字段固定：shots[]（每镜含 zh_direct / en_encoded / neg / duration_s / camera / lighting）
2) 每个镜头 20–60 字中文，动词前置，先主体动作后环境，禁止形容词堆砌
3) 东方审美默认：柔光、低对比、暖中性色温、皮肤通透有质感、留白构图、含蓄情绪
4) 不出现"高清/8K/杰作/best quality"等无效词，改为具体摄影语言（如"85mm 浅景深""侧逆光勾边"）
5) 人物外貌一旦确定，写入 anchors 并在后续镜头逐字复用
6) 负向固定包含：多余手指、肢体畸变、文字水印、脸部模糊、过度磨皮、塑料感
```

**东方审美词典（内置 300 条，示例）**
> 构图：三分留白 / 框景借景 / 中轴对称 / 层层纵深
> 光影：侧逆光勾边 / 窗棂漏光 / 烛光暖调 / 烟雨散射光
> 色彩：黛青 · 月白 · 胭脂 · 藤黄 · 石绿 · 朱砂（低饱和、克制）
> 质感：丝绸垂坠 / 宣纸洇染 / 工笔重彩 / 宋韵极简 / 瓷器釉光
> 人物：东方骨相、内双、肤感通透、素净妆、含蓄表情、衣袂飘逸

**反欧美默认**：不加约束时模型倾向高对比冷调、饱和唇色、过度锐化——提示词引擎必须反向补偿（这是"东方审美优势"的实操点，不是口号）。

## 6. 界面：动态科技感设计系统

### 6.1 设计令牌

```css
:root{
  --bg-0:#05070C; --bg-1:#0A0F18; --bg-glass:rgba(16,24,38,.62);
  --stroke:rgba(120,200,255,.12); --stroke-hot:rgba(53,224,255,.55);
  --cyan:#35E0FF; --violet:#8B5CF6; --amber:#FFB454; --ok:#3DDC97;
  --text-1:#E8F2FF; --text-2:#8FA3BE; --text-3:#5A6B82;
  --r-sm:8px; --r-md:14px; --r-lg:22px;
  --ease:cubic-bezier(.16,1,.3,1); --dur-fast:180ms; --dur:280ms; --dur-slow:420ms;
  --glow:0 0 0 1px var(--stroke), 0 8px 40px -12px rgba(53,224,255,.28);
}
```

### 6.2 四个"科技感"锚点（做对这四个就够了，别堆特效）

1. **背景层**：WebGL 粒子星座 + 缓慢流动的等距网格（Pixi.js，GPU 占用 <3%，`prefers-reduced-motion` 降级为静态渐变）。景深模糊 + 顶部微噪点。
2. **生成中＝实时显影**（杀手级）：接 ComfyUI `/ws` 的 `progress` + latent preview（TAESD/latent2rgb），把每一步的低清预览帧做"由噪点到成形"的渐显动画，叠加扫描线与步数计数。**用户第一次看到画面在眼前长出来，信任感直接建立**。
3. **数据可视化**：显存占用环形表、扩散步数进度、实时 ETA、帧率。数字用等宽字体（JetBrains Mono）+ 滚动补间（240ms，`--ease`）。
4. **交互动效**：卡片 hover 3D 倾斜（`rotateX/Y ≤6°`）+ 边缘光扫过（mask 渐变扫）；节点连线用 `stroke-dasharray` 流光；按钮按下 scale(.98) + 内发光。

### 6.3 布局（1440×900 基准）

```
┌ 左导航 72px ┬──────── 主工作区 ────────┬ 右参数面板 320px ┐
│ 图标+文字   │  L1: 大输入框+3滑块       │ 手风琴：模型/画质 │
│ 生成·模板   │  L2: 模板卡片墙(瀑布流)    │ 时长/运动/风格    │
│ 队列·资产   │  L3: LiteGraph 深色画布   │ 高级(显存/量化)   │
│ 设置        │                          │ 预计耗时·显存条   │
└────────────┴──────────────────────────┴───────────────────┘
     底部：任务队列时间轴 + 缩略图预览 + 批量操作
```
字体：中文 HarmonyOS Sans / 思源黑体；标题字重 600，正文 400，行高 1.65。对比度 ≥4.5:1。

### 6.4 性能纪律
只用 `transform/opacity` 做动效（合成层），禁 `top/left/width` 动画；玻璃层数量 ≤6；L3 画布节点 >80 时关闭连线流光；低端机（核显）自动切"轻量主题"。

# 第二部分：可视化图编辑器 + 创作者插件生态

## 11. 图编辑器技术选型（先解决许可证，再谈像不像）

| 方案 | 许可 | 像 ComfyUI | 结论 |
|---|---|---|---|
| fork `ComfyUI_frontend` | **GPL-3.0** | 100% | ❌ 传染整个前端，闭源商用直接出局 |
| **`litegraph.js`**（jagenjo 原版） | **MIT** | 90%（同源内核） | ✅ **首选**：节点 API 与 ComfyUI 节点作者熟悉的完全一致，社区节点定义可直译 |
| `React Flow` / `@xyflow` | MIT | 60% | 备选：生态现代，但槽位类型/子图/组要自己造 |
| `Rete.js` | MIT | 55% | 不选：数据流模型偏轻，视频管线不够 |

**决策：litegraph.js(MIT) 作图内核 + 自研 Vue3 外壳**。图表内核 MIT、外壳自研 → 整条前端闭源可商用；同时因为内核同源，
「从 ComfyUI 迁移一张工作流」是**语义级直译**而不是重写，这是冷启动创作者供给的关键。

## 12. 插件体系：四类包，一套 manifest

```
packages/
├─ node-packs/    节点包   （新算子/新模型接入，含前端 UI + 可选 Python 算子）
├─ workflow-packs/模板包   （完整工作流 + 参数声明 + 示例产物，创作者主战场）
├─ style-packs/   风格包   （提示词词典 + LoRA 组合 + 调色 LUT，东方审美主载体）
└─ model-packs/   模型包   （权重 + sha256 + 许可声明 + 显存需求）
```

**统一 manifest（`pack.json`）**
```json
{
  "id": "com.creator.dongfang-shuimo",
  "type": "workflow", "version": "1.2.0", "minApp": ">=1.0.0",
  "title": "水墨江南 · 图生视频",
  "author": {"name": "studio-x", "pubkey": "ed25519:..."},
  "i18n": {"zh-CN": {"title": "水墨江南", "desc": "..."}},
  "nodes": [{"id": "com.core.wan-i2v", "range": "^2.0.0"}],
  "models": [{"id": "wan2.1-1.3b-fp16", "size": 2800, "license": "Apache-2.0"}],
  "vram": {"min": 6, "recommended": 12},
  "permissions": ["fs:models", "net:none"],
  "entry": {"front": "ui.js", "back": "op.py"},
  "signature": "base64:..."
}
```

**依赖解析与安装**：`pack.json` 声明节点包版本区间 + 模型需求 → 安装器做拓扑排序，缺失项一次性列清单（含体积与许可），不搞"装到一半报错"。

**安全三件套**（第三方能执行代码，这是商用必须）：
1. 前端插件跑在 `<iframe sandbox="allow-scripts">` + postMessage 桥，零 DOM 权限
2. 后端算子跑独立 venv 子进程：`rlimit` 限内存/CPU、默认断网、声明式权限（`fs:models` / `net:domain`）
3. 发布即签名（ed25519）+ 平台审核 + 首次运行弹「此包申请 X 权限」

## 13. 创作者参与度：把"做模板"变成 15 分钟的事

**核心工具：工作流打包向导（一键出模板）**

```
[当前图] → ① 勾选要暴露的参数（节点控件自动列成清单，可重命名/写中文说明/设范围）
        → ② 自动预检：按目标机型档位跑 3 次 → 显存峰值/耗时/成功率
        → ③ 自动生成：封面(取首帧) + 示例视频 + 适用机型标签 + 参数表单
        → ④ 发布：本地库 / 团队私有市场 / 公共市场
```
这一步做完，作者不需要懂前端代码就能产出可上架的模板——**参与度的天花板由这个向导决定**。

**三视图同一文件（本产品对 ComfyUI 的关键超越）**

| 视图 | 谁用 | 说明 |
|---|---|---|
| 图视图 | 作者/专家 | litegraph 画布，可拖可连 |
| 表单视图 | 使用者 | 由图自动生成：滑块/文本框/图片上传/下拉 |
| 卡片视图 | 小白 | 一张卡 + 三个滑块 + 一个按钮 |

三者是同一份 `workflow.json` 的三种投影：作者改图 → 表单自动重算 → 使用者永不见节点。**这是"可视化"与"新手友好"不打架的唯一解法。**

**表单自动生成算法**
```
walk(graph) → 取标记 exposed=true 的节点控件
  widget.type → form 控件：number→slider(range)，combo→select，
                string(长)→textarea，image→upload，boolean→switch
  生成 schema {key: `${nodeId}.${widgetName}`, label, hint, min/max, default}
提交时按 key 回填 graph，再编译成 ComfyUI API JSON（节点 id 保持稳定）→ /prompt
```
关键约束：**节点 id 在模板内稳定不变**，所以改参数永远不用重建整图。

**社区机制（按留存贡献排序）**
1. 一键「复刻」任何公开模板到自己空间（fork + 派生关系链，原作者可见被使用次数）
2. 模板排行榜（下载/成功率/好评）+ 官方「本周精选」+ 东方美学主题赛季
3. 作者主页 + 收益分成（默认 70/30，认证作者 80/20）
4. 失败率回流：使用者跑挂时自动把失败样本（脱敏）回给作者，形成质量闭环
5. 团队版私有市场：企业内部模板库 + 审核流
6. 可选多人协作编辑（Yjs/CRDT，图上协同）

**编辑器性能纪律**：画布用 Canvas2D 双层（节点层 + 交互层），>300 节点开视口裁剪 + 简绘模式；拖拽期间关阴影与预览；缩放 5%–400%；`Ctrl+K` 命令面板（支持中文拼音首字母搜节点）。

# 第四部分：漫剧模式（电影级观感的最高性价比路线）

## 22. 结论与原理

**能达到「电影级漫剧」，而且这是整条产品线里最容易达标的高质量品类。**

原因：漫剧的工业结构天然规避了 2026 年开源视频模型的三个死穴。

| 漫剧需要 | 开源 i2v 模型能力 | 匹配 |
|---|---|---|
| 分格切镜，单格 1–3s | 3–5s 短片最强 | ✅ 完美 |
| 手部精细操作特写 | 易崩 | ✅ 分镜规避 |
| 严格物理/流体/破碎 | 弱 | ✅ 2D 风格化不需要 |
| 角色跨镜一致 | T2I + LoRA + 参考图可控 | ✅ 可解 |
| 口型对白 | 专用模型可解 | ✅ 可解 |
| 镜头推移/视差 | 2.5D + zoompan 可解 | ✅ 可解 |
| 长镜头连续动作 >8s | 漂移严重 | ❌ 不需要 |

**判定边界**

| 等级 | 定义 | 可行性 |
|---|---|---|
| L1 动态漫 | 分格 + 轻动效 + 配音 | 100% 稳定量产 |
| **L2 电影级漫剧** | 多层视差 + 演出设计 + 声音设计 + 调色 + 转场 | ✅ 可达（含人工"导演"环节） |
| L3 电影级连续动画 | 角色转身/连贯打斗/长镜头运镜 | ❌ 不可达，需传统动画或 3D |

## 23. 漫剧专用产线（7 段）

```
① 角色设定集   三视图 + 4 表情 + 3 服装 + 光调卡（一次做好，全剧复用）
② 剧本 → 分镜表  LLM 输出 JSON：格号/景别/机位/画面/台词/时长/情绪/音效提示
③ 逐格关键帧    Qwen-Image + 角色 LoRA + ControlNet 构图锁 + IPAdapter 参考
④ 动效层        三选一：zoompan 多层视差 ｜ 局部 i2v 1–2s ｜ 粒子光效叠加
⑤ 口型          仅正面近景用 LatentSync/Wav2Lip，侧背景不用
⑥ 声音          CosyVoice2 配音(多音字校正) + 音效库 + BGM + ducking
⑦ 剪辑合成      格间转场/节奏点/字幕烧录/调色/漫画质感(网点·描边·赛璐璐阴影)
```

**关键认知**：漫剧的"电影级"70% 来自**演出与声音设计**，不是分辨率。所以产品必须内置"导演层"——
运镜预设（推/拉/摇/跟/环绕）、节奏模板（紧张 0.8s/格 · 抒情 2.5s/格）、音效库、转场库。这是护城河。

## 24. 漫剧质量硬指标

| 指标 | 目标 | 为什么比写实更高 |
|---|---|---|
| 角色一致性 DINO | ≥0.88 | 观众对角色脸极敏感，0.05 漂移就"换人" |
| 口型偏差 | ≤80ms | 台词密，错位立刻出戏 |
| 线条稳定 | 无"呼吸"抖动 | 逐帧重绘会导致线条游走，必须锁 seed + 固定 ControlNet |
| 镜头运动 | 24/30fps 缓动无阶梯 | zoompan 要走 subpixel + 贝塞尔缓动 |
| 单集规格 | 竖屏 1080×1920 · 60–180s · 18–30 格 | 抖音漫剧标准 |
| 单集一次通过率 | ≥80% | 含自动重跑 |

## 25. T0（8G）机型实测预期

| 环节 | 耗时（RTX 5060 8G） |
|---|---|
| 单格关键帧 1536×864 / 24 步 | 30–50s |
| 局部 i2v 1.5s / 480p | 60–90s |
| 2× 超分 + zoompan 渲染 | 15–25s/格 |
| 配音 + 口型（近景） | 20–40s/格 |
| **一集 24 格（含 QC）** | **25–40 分钟** |

对比写实视频 15s 需 15–25 分钟——**8G 卡做漫剧的单位时间产出高 3–5 倍，是这台机器的最优商业解**。

# 第五部分：全板块参数化与自定义设计体系

## 27. 参数五层架构（谁能改什么）

```
L0 系统硬约束   显存方程/模型能力上限     用户不可见
L1 机型预设     由探测+标定自动生成       用户可覆盖但会提示风险
L2 模板默认     作者在打包时设定          使用者改则模板标记"已自定义"
L3 用户常用     每个板块 3–8 个核心参数   界面直接露出的滑块
L4 高级裸参     全量参数（30–80/板块）    折叠区 / 专家模式 / 导入导出
```
原则：**任何 L4 参数都能被覆盖，但覆盖后必须重算显存/耗时并给出风险提示**。自定义的自由度不设上限，只设护栏。

  "type": "int", "min": 8, "max": 50, "step": 1, "default": 24,
  "unit": "步",
  "label": {"zh": "采样步数"},
  "hint": {"zh": "步数越高细节越多，超过 30 步收益急剧下降"},

# 第六部分：意图对齐与逐帧画质提升

## 33. 可控性：四把锁 + 收敛闭环

「玩家生成最符合预期的画面」本质是两件事：**把意图拆成可独立锁定的维度**，以及**允许迭代收敛**。

**四把锁（每一把都可单独锁死，锁住后全流程不变）**

| 锁 | 输入 | 技术 | 典型用法 |
|---|---|---|---|
| 构图锁 | 手绘草图 / 参考图 / 九宫格框 | ControlNet lineart+canny (权重 0.6–1.0) / 深度图 | 我要这个站位、这个留白 |
| 角色锁 | 角色三视图 + 表情包 | IPAdapter(0.6–0.9) + 专属 LoRA(0.7–1.0) + 面部锚点 | 十集都是同一张脸 |
| 光影锁 | 色温滑块 / 光位 / 光比 | 提示词分区 + IC-Light 类重打光 | 要黄昏侧逆光 |
| 风格锁 | 风格预设包 | LoRA + LUT + 提示词词典 | 要赛璐璐不要厚涂 |

**收敛闭环（这是"最符合预期"的工程本质）**
```
一句话意图 → 生成 4 候选 → 九宫格并排选 1 → 对选中图局部改(mask 重绘)
→ 参数微调(±) → 再生成 4 候选 → …… 收敛后「冻结」为镜头基准
```
不是"一次生成对就中"，而是**三次迭代必收敛**的设计。冻结后的镜头进入量产，后续帧只允许在光流约束下变化。

## 34. 画质七阶阶梯（细节从哪来）

**核心认知：1080p 的清晰度不来自"最后放大一下"，来自每一级都注入新信息。纯插值超分只会把糊放大。**

| 阶 | 操作 | 输出 | 新增信息 | 8G 耗时 |
|---|---|---|---|---|
| 0 | base T2I 1024·24步 | 1024 | 构图 · 主体 · 大体光影 | ~40s |
| 1 | hires-fix 1.5× 去噪 0.45·12步 | 1536 | 局部重绘补结构细节 | +35s |
| 2 | **局部重绘**（脸/手/眼专项） | 1536 | 面部器官、指节、瞳孔高光 | +25s/处 |
| 3 | 分块超分 2×（tile 1024 / overlap 64） | 3072 | 纹理重建（织物/皮肤/木石） | +60s |
| 4 | 低去噪纹理 pass（0.15–0.25） | 3072 | 材质颗粒、微对比 | +45s |
| 5 | 合成 + 光调 + LUT | 3072 | 色彩层次与光比 | +5s |
| 6 | USM(1.2/0.35) + 颗粒 3–6% | 3072 | 观感锐度、去塑料感 | +2s |

**没有第 2 和第 4 阶，画面一定"软、假、塑料"**——这是绝大多数人做不出商用画质的真正原因。

## 35. 逐帧质量的正确做法（关键工程结论）

**逐帧独立精修 = 必然闪烁。** 正确结构：

```
镜头首帧 ── 全七阶精修 ──▶ 基准帧(3072)
   │
   ├─ 关键帧(每 8 帧 / 近景 / 焦点帧) ── 完整七阶 ──▶ 锚点帧
   ├─ 中间帧 ── 光流 warp + 低去噪 pass(0.15–0.25) + 时序降噪 ──▶ 继承细节
   └─ 全片 ── deflicker + 光流稳定 + 统一 LUT ──▶ 一致性闸门
```
- **细节靠锚点帧注入，靠光流传播**，这样既锐又不抖
- 中间帧去噪值必须 ≤0.25，否则线条/纹理逐帧重绘产生"呼吸"
- 时序降噪（temporal denoise）权重 0.3–0.5，是"细节能留住"的保险

## 36. 单帧质量客观验收（不靠嘴说）

| 指标 | 目标 | 工具 |
|---|---|---|
| 拉普拉斯方差（锐度） | 中位数 ≥ 目标阈值（按题材标定） | OpenCV |
| 边缘密度 | 与参考基准 ±15% 内 | Canny 计数 |
| 色彩熵 | ≥ 阈值（防灰防死） | 直方图 |
| BRISQUE / NIQE | 越低越好，取相对排序 | 现成实现 |
| 帧间亮度 std（闪烁） | < 2% | 时序统计 |
| 光流残差 | 相邻帧 warp 残差低于阈值 | Farneback/RAFT |
| VLM 五维分 | ≥ 4.0（商用档） | Qwen3-VL |

## 37. 8G 机的时间预算分配（把时间花在刀刃上）

单镜 5s（120 帧 @24fps）总预算约 6–8 分钟：

| 环节 | 占比 | 说明 |
|---|---|---|
| 关键帧基准（七阶） | 25% | 决定整镜上限，不能省 |
| 锚点帧（3 个） | 30% | 每 8 帧一个锚点，近景加密 |
| i2v 生成 | 30% | 480p 生成，细节交给锚点 |
| 后处理链 | 15% | 超分/补帧/调色/质检 |

**结论：宁可降 i2v 分辨率，也不要降关键帧精修阶数**——观众感知的是"脸和材质的细节"，不是原生像素数。

# 第七部分：MiniMax H3 主引擎 + 逐帧可视化交互

## 38. 双引擎架构（H3 为主，本地为辅）

MiniMax H3 为闭源视觉模型（以官方 API 接入），因此架构必须是**主辅双引擎 + 智能路由**，
而不是"单模型一把梭"。本地部署的部分由开源栈承担，H3 承担它最强的那一段。

```
                ┌────────── 意图解析 / 提示词适配(本地 LLM) ──────────┐
                ▼                                                    │
        ┌───────────────┐   路由决策(质量/成本/隐私/网络)             │
        │  任务编排器    │───────────────────────────────────────────┤
        └───┬───────┬───┘                                           │
            │       │                                               │
   ┌────────▼──┐ ┌──▼─────────────────┐                             │
   │ H3 主引擎  │ │ 本地开源引擎        │                            │
   │ (API)     │ │ ComfyUI            │                            │
   │·语义理解   │ │·批量/离线/隐私      │                            │
   │·高质量生成 │ │·超分 补帧 局部重绘  │                            │
   │·首帧图生视频│ │·角色一致性 LoRA    │                            │
   └────┬──────┘ └──┬─────────────────┘                            │
        └─────┬─────┘                                                │
        ┌─────▼──────────────┐                                       │
        │ 统一产物层 帧级索引 │◀──────────────────────────────────────┘
        └─────┬──────────────┘
        ┌─────▼──────────────────────────────────────┐
        │ 帧检查器 Frame Inspector（逐帧可视化交互）  │
        └────────────────────────────────────────────┘
```

**路由规则（可配置，默认如下）**

| 场景 | 引擎 | 理由 |
|---|---|---|
| 要最高画面质量、语义复杂的长句描述 | **H3** | 视觉理解与生成质量最强 |
| 480p 草稿试错（改参数刷候选） | 本地 | 零边际成本，秒级反馈 |
| 已定稿要出 1080p 成片 | **H3** | 一次到位，质量上限高 |
| 批量 20 集漫剧（成本敏感） | 本地为主 | 单集成本压到电费 |
| 断网 / 隐私敏感 | 本地 | 不外传 |
| 超分/补帧/局部重绘/口型 | 本地 | H3 不做这些后处理 |
| H3 限流或失败 | 本地兜底 | 不断产 |

**若 H3 后续开放权重**：`model adapter` 层一天内切换为本地推理，上层零改动。

## 39. H3 的五项工程优化

| 优化 | 做法 | 收益 |
|---|---|---|
| **提示词适配器** | 中文口语 → H3 偏好的结构化长句（主体+动作+场景+镜头+光线+质感），剥离无效词（"8K/杰作"），中文原生无需翻译 | 命中率显著提升 |
| **草稿-定稿两段式** | 本地 480p 出 4 候选并选定 → 同参数交 H3 出 1080p | 成本降 60–80% |
| **分段续接** | H3 单次时长有限 → 上一段尾帧作下一段首帧 + 交叉淡入 8–12 帧 | 突破单次时长限制 |
| **参数网格** | 一次并发提交 4 组参数（运动幅度/镜头），选中即存为预设 | 一次调用拿 4 个方案 |
| **结果缓存** | `hash(prompt+params+model_version)` → 命中直接复用资产 | 重跑免费，改一参数只花一份钱 |

必做的工程细节：限流队列（指数退避）、失败自动重试 2 次、成本实时累计与预算上限、
`[MINIMAX_API_KEY]` 走本地密钥库不落日志。

## 40. 帧检查器（Frame Inspector）——本产品的交互核心

**设计目标：让"每一帧"都成为可看、可判、可改的对象。**

```
┌──────────────────────────────────────────────────────┐
│ 画面区  分屏对比(A/B) │ 洋葱皮 │ 放大(至 800%) │ 网格  │
├──────────────────────────────────────────────────────┤
│ 质量热力条  每帧一格 ▮▮▮▯▮▮  颜色=质量分  点击直达    │
│ 叠加曲线: 亮度 / 锐度 / 光流残差（三条可选显隐）        │
├──────────────────────────────────────────────────────┤
│ 时间轴  帧号 · 时间码 · 锚点标记◆ · 关键帧◇ · 问题帧▲   │
├──────────────────────────────────────────────────────┤
│ 帧操作 锁定🔒 重绘🎨 替换↻ 导出↓ 设为锚点◆ 插入补帧＋   │
├──────────────────────────────────────────────────────┤
│ 右侧  该帧参数快照 · 局部 mask 画笔 · 提示词微调 · 重跑  │
└──────────────────────────────────────────────────────┘
```

**四种模式（一键切换，同一份数据）**

| 模式 | 用途 | 交互 |
|---|---|---|
| 播放模式 | 正常看片 | 空格播放，拖拽擦洗 |
| 检视模式 | 逐帧审片 | 方向键逐帧、放大镜、contact sheet 缩略图墙 |
| 修复模式 | 修问题帧 | 红帧列表 → 逐帧重绘 → 回填，批量一键跑 |
| 对比模式 | 选优 | A/B 分屏、版本差异热图、参数差异表 |

**质量热力条的数据模型（前端最关键的 24px）**
```ts
type FrameQuality = {
  frame: number;
  score: number;        // 0-100 综合
  sharp: number;        // 拉普拉斯方差归一
  flicker: number;      // 与前一帧亮度差
  flowResidual: number; // 光流 warp 残差
  status: 'ok' | 'warn' | 'bad';
};
// 颜色：ok=#3DDC97 warn=#FFB454 bad=#FF5C7A，高度按 score 画柱状
```
这一条 24px 的色带，就是「平台生成能力」最直观的可视化——**用户一眼看到 120 帧里哪 3 帧崩了，点击直接修**。

## 41. 让玩家"真切感受生成能力"的三个交互

1. **实时显影（Live Reveal）**：接生成端进度与潜空间预览，画面从噪点逐步成形，
   叠加步数计数与耗时；H3 通话中显示「排队→理解→生成→解码→后处理」五段真实状态。
2. **参数因果即时反馈**：拖动任意滑块（运动幅度/景深/光位），立刻用**已缓存的首帧**做
   3 档对比小图（低/中/高），不消耗生成额度。让"参数有什么用"变成看得见的事。
3. **单帧手术**：在画面里圈一个区域 → 只重绘这一块 → 前后对比滑杆。
   **这是让用户从"抽卡"变成"创作"的关键一帧。**

## 42. 交互性能纪律

- 时间轴与热力条用 Canvas 绘制（120 帧 × 多曲线，DOM 会卡）
- 帧图走 `IndexedDB + 低清代理`，擦洗只加载 ±30 帧窗口
- 所有高亮/动画走 `transform/opacity`
- 120 帧首屏渲染 <120ms，擦洗延迟 <16ms（60fps 跟手）
